# Maestro E2E 테스트 규칙

> Maestro 공식 문서 및 내부 테스트 가이드 참조

---

# E2E 테스트 핵심 철학

## 사용자에게 보이는 동작을 테스트할 것

- 사용자가 실제로 보고 상호작용하는 요소를 기준으로 테스트합니다.
- 내부 구현 방식보다 렌더링된 UI 상태를 검증합니다.
- 화면에 표시되는 텍스트, 버튼, 로딩 상태, 네비게이션 결과를 우선 검증합니다.

---

## 상태 전환(State Transition)을 검증할 것

- 사용자 액션 이후 화면 상태 변화를 검증합니다.
- 로딩 → 성공 / 실패 상태 변화를 확인합니다.
- 네비게이션 이후 올바른 화면이 렌더링되는지 검증합니다.

---

## 안정적인 Assertion 우선 사용

- 안정적인 UI 요소를 기준으로 assertion 작성
- 일시적으로 변하는 UI 상태에 의존하지 않기
- 예측 가능한 렌더링 지점을 기준으로 검증하기

---

## 테스트는 독립적으로 실행 가능해야 함

- 각 테스트는 단독 실행 가능해야 합니다.
- 이전 테스트 상태에 의존하지 않습니다.
- 필요한 경우 앱 상태를 초기화합니다.

---

## 실제 사용자 플로우 중심으로 테스트

- 내부 구현 커버리지보다 실제 사용 시나리오를 우선합니다.
- 로그인, 폼 제출, 화면 이동, 에러 처리, 재시도 흐름 등 실제 사용자 행동을 테스트합니다.

---

## 비동기 UI를 안전하게 처리할 것

- 임의 대기 시간 대신 렌더링 완료 상태를 기다립니다.
- assertVisible 또는 extendedWaitUntil 사용
- 필요 시 로딩 UI가 사라졌는지까지 검증합니다.

---

## 구현 세부사항보다 사용자 행동을 테스트할 것

- 내부 상태나 구현 구조보다 사용자 관점의 동작을 검증합니다.
- 테스트는 “어떻게 구현되었는가”보다 “사용자에게 어떻게 보이는가”에 집중해야 합니다.

---

# DO

- 파일명은 kebab-case 및 영문만 사용
- 하나의 기능 = 하나의 파일
- 요소 선택 우선순위:
  - 텍스트 > testID > index
- 동적 UI에는 optional: true 사용
- 명시적 대기 대신 assertVisible 사용
- 가독성을 위한 섹션 주석 작성

---

# DON'T

- 하드코딩된 대기 시간 사용 금지


- wait: 5000


- 동적으로 변하는 텍스트를 셀렉터로 사용 금지
- 하나의 파일에 너무 많은 플로우 작성 금지
- 내부 구현 세부사항 직접 테스트 금지
- 실행 순서에 의존하는 테스트 작성 금지
