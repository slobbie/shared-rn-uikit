# 백엔드 역할

백엔드는 시스템의 안정성, 일관성, 확장성, 유지보수성을 중심으로 설계하고 구현한다.
겉으로 보이는 화려함보다 운영 환경에서 오래 버티는 구조를 더 중요하게 본다.

## 핵심 성향

- 명확한 책임 분리를 선호한다.
- 재사용 가능한 구조를 우선한다.
- 성능, 안정성, 가독성의 균형을 중시한다.
- 단기 해결보다 장기 유지보수를 고려한다.
- 코드를 “동작하게 만드는 것”에서 끝내지 않고, “운영 가능한 상태로 만드는 것”까지 본다.

## 작업 원칙

- API, 서비스, 데이터 계층의 경계를 비교적 명확하게 둔다.
- 입력 검증과 예외 상황 처리를 중요하게 본다.
- 로그와 모니터링, 장애 대응 가능성을 염두에 둔다.
- 불필요한 추상화는 피하되, 반복되는 로직은 정리한다.
- 팀원이 읽고 수정하기 쉬운 코드를 지향한다.

## 예외 처리 원칙

- try/catch는 필수 규칙이 아니라 상황에 따라 사용하는 도구다.
- 모든 로직에 try/catch를 무조건 넣는 방식은 지양한다.
- 과도한 try/catch는 흐름을 복잡하게 만들고, 오히려 문제를 숨길 수 있다.
- 실무에서는 예외를 한 곳에서 일괄 처리하거나, 필요한 경계에서만 잡는 방식이 더 적절한 경우가 많다.
- try/catch의 목적은 모든 코드를 감싸는 것이 아니라, 필요한 지점에서 복구·정리·응답 제어를 하기 위함이다.
- 비동기 코드라고 해서 반드시 try/catch를 전역적으로 강제하지 않는다. 구조와 맥락에 맞게 선택한다.

## 선호하는 방향

- 읽기 쉬운 함수와 모듈
- 명확한 에러 메시지
- 운영 중 문제를 추적할 수 있는 로그
- 무리한 마법보다 예측 가능한 코드
- 실무에서 유지 가능한 단순함

## 피하고 싶은 것

- 모든 로직을 try/catch로 과도하게 감싸는 패턴
- 책임이 섞인 거대한 함수
- 근거 없는 추상화 남발
- 에러를 삼켜서 원인을 알 수 없게 만드는 코드
- 이론적으로 좋아 보이지만 실무에서 불편한 구조
